# CampusOverflow 团队章程 v1 草案

状态：待 A、B、C 全员确认。

仓库 main 和当前 PR 中未发现已经确认的团队章程。本文件仅整理一份可评审草案；下列规则在全员确认前均不得表述为既有共识。

## 1. 当前角色分工

- A：Q&A、Identity 增量。
- B：Reputation、整体测试与覆盖率统筹。
- C：Discovery、前端增强、文档汇总、流水线验证与最终交付。

分工可以经全员确认后调整。调整时应在文档和 Sprint Backlog 中同时记录负责人、范围与生效时间。

## 2. 团队价值观草案

- 真实：运行结果、进度和证据如实记录，不以配置存在代替验证通过。
- 可追溯：需求、设计决策、代码和验收结果均能关联到故事、任务、提交或 PR。
- 小步协作：按任务拆分改动，尽早暴露契约依赖和阻碍，避免跨成员范围的大批量修改。
- 质量共同负责：成员负责本人模块，整体测试、评审和交付由团队共同完成。

## 3. 沟通与决策草案

- 需求、接口、错误码和架构决策以仓库文档、ADR 或 PR 讨论为可追溯依据。
- 阻碍其他成员的接口变化应尽早在 PR 中说明；未获得确认前，不修改其他上下文的公共契约。
- 状态更新必须区分计划、已实现、已验证、已合并；mock、自测和真实 E2E 分开记录。
- 会议、访谈、评审和截图仅在实际发生并留有证据后归档。
- 即时沟通渠道、例会频率和响应时限尚待全员选择并补充。

## 4. 开发规范、分支与评审草案

- main 只接收经过 PR 评审的改动；功能分支采用 `feature/<成员>-<主题>`，修复分支采用 `fix/<主题>`。
- 禁止直接推送 main、强制推送共享分支或绕过分支保护。
- 一个 PR 聚焦一个范围，列明验证结果、未完成事项和跨模块依赖。
- 不删除测试、不放宽断言、不降低覆盖率或架构门槛来掩盖失败。
- 公共 API、事件契约、错误码和数据库迁移的改动需要在 PR 中明确影响面并取得相关负责人确认。
- 作者不能代替队友批准自己的 PR。需要一名还是两名非作者批准，待团队结合仓库保护规则确认。
- 上游变化与本地未提交工作冲突时，先保护已有改动，再讨论同步方式，不直接重置覆盖。

## 5. Definition of Done 草案

一项任务只有满足适用条件后才能标为“已验证”或“已完成”：

1. 实现范围与故事、测试或文档要求一致，没有擅自降低验收标准；
2. 单元测试、类型检查、构建及适用的架构检查实际通过；
3. 跨上下文功能完成真实接口联调，mock 结果不算真实 E2E；
4. 涉及数据库、容器或部署时，保存可复现命令、版本和真实结果；
5. PR 已说明风险、依赖和未完成项，并完成团队约定数量的评审；
6. 必要文档、截图和演示步骤已归档，且证据与结论一致；
7. 合并 main 后重新验证受影响的流水线。
