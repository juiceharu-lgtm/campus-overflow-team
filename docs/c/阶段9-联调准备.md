### JDBC 默认编码缺陷复现与修复

- Spring Boot 3.4.5 依赖管理实际选择 MySQL Connector/J 9.1.0。使用仓库默认 URL 的 `characterEncoding=utf8mb4` 启动时，Flyway 获取连接失败，根因链最终为 `java.io.UnsupportedEncodingException: utf8mb4`。
- MySQL 官方 Connector/J 文档要求 `characterEncoding` 使用 Java 编码名；`characterEncoding=UTF-8` 会映射为 MySQL `utf8mb4`。数据库、表和 Compose 仍保持 `utf8mb4`，只需把 JDBC 客户端参数改为 `UTF-8`。
- 独立分支 `fix/jdbc-character-encoding` 的本地提交 `bce74ae` 只修改 `co-bootstrap/src/main/resources/application.yml` 一行。修复后应用使用默认 URL 成功连接 MySQL 8.0.39、验证 5 个 Flyway 迁移并达到 readiness `UP`。
- 使用 Connector/J 9.1.0 实际写入并读回 `中文跳表验证😀`，字符串完全一致；ngram 全文搜索“跳表”命中 1 条。固定验证行随后删除，数据库复核计数为 0。

## 5. 手工真实验证清单

### 5.1 主链路

1. 通过前端或 API 获取 CSRF Cookie，注册两个独立学生账号 U1、U2并分别登录；保留独立浏览器会话。
2. U1发布带中文标题、正文和标签的问题，记录 `questionId`。
3. U2提交回答，记录 `answerId`。
4. U1调用 `PUT /api/v1/questions/{questionId}/accepted-answer` 采纳 U2回答。
5. 等待 outbox中继（默认500ms轮询），检查事件 `published_at`、`attempts`、`last_error`。
6. 查询 `GET /api/v1/users/{U2}/reputation`，预期采纳奖励和 `FIRST_ACCEPTED` 徽章符合规则。
7. 查询 `GET /api/v1/search/questions?q=跳表`，预期命中该问题且 `accepted=true`。
8. 用 U2查询 `GET /api/v1/notifications` 与 `/unread-count`，预期出现 `ANSWER_ACCEPTED`；分别验证单条已读和全部已读。

### 5.2 登录与权限

- 未登录写操作应返回401；登录请求缺少 CSRF 应返回403和 `AUTH-403-CSRF`。
- 非作者编辑/删除问题或回答应被拒绝；其他学生采纳应返回 `QA-3001`。
- 自己给自己的问题/回答投票应返回 `QA-1015`。
- 他人查看声誉流水应返回 `REP-3002`；本人和管理员按规则允许。
- 通知列表和已读操作必须限定当前用户；越权预期使用 DIS-3001，但需先完成 PR #4 的团队确认与登记。
- 教师/助教/管理员场景需要真实课程角色；不能用前端伪造角色或直接修改响应。

### 5.3 悬赏

- 控制器边界：积分10～500，期限1～14天；分别提交9、501、0、15验证参数拒绝。
- 学生发起悬赏应被拒绝；课程教师、助教或管理员才可发起。
- 验证可用积分不足 `REP-1002`、范围错误 `REP-1003/REP-1004`、重复/已结束状态冲突。
- 发起后核对可用积分减少、冻结积分增加；采纳后核对奖励或退款规则；重复事件不得二次扣减/奖励。

### 5.4 中文搜索与软删除

- 先确认 MySQL实际 `ngram_token_size=2`，再用至少两个字符的中文词项搜索；单字符或非法词项按 `DIS-1001` 处理。
- 发布含唯一中文词的题目，等待投影后检查全文搜索、标签过滤、排序、未回答/悬赏筛选和分页。
- 另建无回答问题，由作者软删除；确认 `qa_question.deleted_at` 非空、详情按规则不可见、搜索投影标记删除且结果排除。
- 验证有回答问题的作者删除限制以及课程管理者权限，不通过物理删除绕过领域规则。

### 5.5 事件幂等

只在一次性测试数据库中执行：

1. 记录目标 `event_id`，以及 `rep_ledger`、`processed_event`、`dis_notification` 的处理前行数。
2. 将同一 outbox事件重置为待投递，清除租约并等待中继再次发送；不要修改payload。
3. 验证相同 `event_id` 不会新增第二条声誉流水、通知或搜索副作用；`processed_event` 和数据库唯一键应兜底。
4. 检查 outbox `attempts`、`last_error` 和 `co_outbox_*` 指标，保存前后对比。

重放属于测试数据库操作，必须记录 SQL、事件ID和数据库快照；不得在共享或生产数据库执行。

## 7. 课程PDF与初始框架差异及最小方案

### 7.1 包管理与前端质量

课程 Lab5（PDF文件第8～9页，正文第55～56页）要求 Node20+，推荐pnpm，并把 `pnpm dev`、`pnpm lint`、`pnpm typecheck` 和 pre-commit拦截列为提交物。初始框架和CI实际使用 npm，且 main 的 `package.json` 没有 `lint` 脚本或 Husky配置；PR #5 使用 npm并新增 `package-lock.json`。

最小处理方案：

1. 当前继续按仓库既有 npm/CI 和 PR #5 锁文件完成联调，不擅自切换包管理器，也不同时维护两种锁文件。
2. 向教师确认“推荐pnpm”是否允许项目沿用 npm；保留确认记录。
3. 若课程严格要求 pnpm，另开独立工具链 PR，一次性迁移锁文件和CI，并重新验证；不要混入业务联调分支。
4. ESLint、Prettier、Husky/pre-commit 属于当前确实缺失的 Lab5 项，应作为独立质量任务补齐，不能用 typecheck/build 代替。

### 7.2 覆盖率与质量门禁

课程 Lab7（PDF文件第11～13页，正文第58～60页）要求团队单测覆盖率70%以上、核心聚合90%+，并接入 SonarQube + JaCoCo + Checkstyle；Sonar门禁为 Coverage >70%、Bugs=0、Vulnerabilities=0。README要求领域层至少70%，而父 POM 当前门槛为0，注释又写 Sprint4前提升到0.80。

最小处理方案：

1. 业务完成后先保持配置不变生成 JaCoCo报告，得到真实基线，不为绿灯修改测试或阈值。
2. 团队与教师确认0.70和0.80的最终门槛；随后只在一个专门PR中调整属性并保存前后报告。
3. 核心聚合90%+单独从报告核验，不能只用全局平均值掩盖核心类不足。
4. SonarQube和Checkstyle当前不在现有CI中，应另列质量门禁任务；本阶段不重写CI。
