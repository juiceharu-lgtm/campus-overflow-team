实现时必须保持的边界：

1. 保持模块化单体五层结构；领域层不依赖 Spring/JPA，应用层编排领域对象和端口。
2. 跨上下文只依赖公开 API 或集成事件，不直接访问其他上下文的表、JPA 仓储或内部领域对象。
3. Q&A 事务通过 transactional outbox 发布事件；投递语义为至少一次，Discovery 消费端必须幂等。
4. 中文搜索经 `SearchPort` 隔离；MySQL 使用 ngram，单个词项至少 2 个字符、最多 5 个词项。
5. 软删除内容必须从搜索投影中消失，但不能物理删除业务历史。
6. API 错误遵循 RFC 9457 和 `DIS-*` 错误码分段。
7. Identity 参考实现表明：规则放在聚合/值对象，事务和跨端口调用放在应用服务，API 实现把领域对象翻译为发布语言，JPA 转换留在基础设施层。

### 5.2 建议补充的关键场景

- `SearchQuery`：`null`/空白/全运算符输入；恰好和超过 50 个 Unicode 码点；超过 5 词截断；混合空白；无关键词时强制从 relevance 降级到 newest；分页默认值。
- `MentionParser`：`null`/空串；中英文标点边界；昵称 2/20/21 字符；重复顺序；第 6 人截断；邮箱和连续 `@`；Unicode 昵称。
- `RelatedQuestionPolicy`：空并集、零 shared、异常计数；相似度相同后的得分/采纳次序；空候选、非正 limit、limit 大于候选数；稳定、确定性的最终次序。
- `Notification`：创建后默认为未读；必要字段；本人重复标记幂等；他人越权及准确错误码。
- `DiscoveryQueryService`：一次批量身份查询、缺失用户降级、分页字段不丢失；当前问题无标签；候选排序、相似度及 limit。
- `NotificationProjector`：6 类事件逐一验证收件人、类型、标题、链接；提及去重/未知昵称/本人；重复事件不重复保存；仓储唯一约束冲突策略。
- `NotificationService`：列表和未读数严格按本人；不存在与越权；单条/全部已读；视图映射。
- `SearchIndexProjector`：9 类事件的正确投影动作；重复事件完全无副作用；回答删除不产生负数；投票增量；问题软删除；三种悬赏状态事件。

测试新增应放在对应模块测试目录，以 mock/fake 端口隔离上游上下文；不得为了绿灯删除测试、改断言或降低覆盖率。

## 6. 与 A、B 的接口和事件依赖

### 6.1 A：Q&A 与 Identity

Discovery 只通过以下公开契约依赖 A 的范围：

- `IdentityApi.findUser/findUsers/findByDisplayName` 与 `UserSummary`：搜索作者批量回填、通知标题昵称、`@昵称` 解析。
- `QaQueryApi.findQuestion` 与 `QuestionRef`：通知投影需要的问题标题、作者、课程、采纳/删除信息。
- Q&A 事件：`QuestionPostedEvent`、`QuestionEditedEvent`、`AnswerSubmittedEvent`、`ContentDeletedEvent`、`AnswerAcceptedEvent`、`AnswerEndorsedEvent`、`VoteCastEvent`、`CommentPostedEvent`。

C 不修改 A 的聚合、应用服务或事件生产逻辑。若事件字段或时序存在问题，先以公开契约和测试复现后交由 A 处理。

### 6.2 B：Reputation

Discovery 订阅 B 范围内的：

- `BountyOpenedEvent`、`BountyAwardedEvent`、`BountyClosedEvent`：搜索投影悬赏状态；获奖通知。
- `BadgeAwardedEvent`：徽章通知。

`ReputationChangedEvent` 当前不被 Discovery 消费。C 不修改 B 的账本、悬赏、徽章、排行榜实现或覆盖率统筹配置；只对公开事件做消费者侧验证。

### 6.3 数据一致性边界

Discovery 是纯下游/最终一致的读模型。目前不向其他上下文发布接口或事件。事件至少一次投递，因此：

- 搜索计数/状态投影依赖 `ProcessedEventStore`；
- 通知依赖 `(sourceEventId, recipientId)`；
- 联调关注“事件已落 outbox → relay 投递 → Discovery 投影更新”的链路，而不是把跨上下文更新塞进同一业务事务。

## 7. 推荐实施顺序与等待关系

### 7.1 推荐顺序

1. **领域层第一批：`SearchQuery`、`MentionParser`**。规则小、输入输出确定，先补边界测试，可快速建立稳定基线。

4. **事件投影：`SearchIndexProjector`、`NotificationProjector`**。逐事件做幂等和副作用单测。
5. **模块验证**：在 JDK 21 环境运行 Discovery domain/application 测试，再验证基础设施适配器和 MySQL ngram 行为。
6. **整体联调**：与 A 的 Q&A/Identity、B 的 Reputation 契约联调。
7. **最终验证**：全流水线、端到端链路、压测和演示材料汇总。
